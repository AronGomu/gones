Repository facts

Why foundation decisions come first

Architecture documents describe

  • Product named MTG Winds: public Legacy tournament discovery plus managed registration.
  • Independent Angular SPA plus ASP.NET Core .NET 10 REST API, PostgreSQL, EF Core, JWT, OAuth, Docker.
  • Users, organizations, organizer/admin authz, tournament lifecycle, registrations, reminders, audit, soft delete.
  • Production success criteria covering account creation through event participation.

Current repository implements

  • Product named Gones: leagues, live tournament operation, rounds, results, standings, player stats.
  • Angular 21 PWA deployed statically; browser localStorage is active backend.
  • No current accounts, auth, organizations, role mgmt, server, DB, email provider, or scheduler.
  • Existing calendar/event CRUD, event detail pages, ICS export, local persistence, plus dormant Nest API adapter.
Core mismatch: docs define separate backend-backed pre-event platform. Current app defines frontend-only event-results product. Tournament, user/player, delete, backend, ownership, deployment semantics overlap but disagree. Choosing details before merge model would silently assume product direction.
