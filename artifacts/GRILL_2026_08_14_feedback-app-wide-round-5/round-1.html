1. Private data — localStorage literally, or user-scoped store?

You asked every page to cache "exactly like Calendar" = plain localStorage; but Calendar caches anonymous public data, while Registrations, Settings and admin lists are private rows that would then outlive logout and be readable by the next account on the same browser.

2. Stale cache on mutating pages

Grant a role on the admin Users page and the cached list would keep showing the old role for up to 24 hours — the page would appear to lie about the change you just made.

3. Your question — player stats storage

You offered two options. Facts that decide it: the global rankings endpoint already loads every completed league document and recomputes per request, and the player page downloads every league to the browser — both are O(all data) per view and both die at 100×. Tournaments land a few per week, so the write side is nearly free.

4. Match history delivery

Stats are ~20 numbers, but the match list is unbounded and the page filters, sorts and pages it locally today — that behaviour is what your archetype and layout asks build on.

5. Event rename blast radius

You said DOMAIN CHANGE, URL and all data names. On the frontend "calendar" is currently a route, a directory, ~12 component/service files, ~120 i18n keys, ~400 data-cy attributes, two localStorage keys and a Cypress suite. Depth changes this from ~2 tickets to ~5.

6. Killing Organization ownership

"No one owns an Organization" is a backend domain change, not a form tweak: OrganizationRoles.Owner gates publishing, and account closure today refuses to close an account that solely owns an organization unless you name a successor (a whole transfer flow in AdminAccountService and OrganizationService).

7. Making 100× data

The demo environment is hand-written JSON seeded through the real HTTP API, replaying every Live command. 100× that is roughly 700 accounts, 200 organizations, 1600 Events, 200 League Archives and their rounds — through HTTP that is a very long seed and a repository full of generated JSON.

8. Stress dataset shape

"Multiply all current numbers by 100" taken literally includes accounts — 700 registered users, each needing a password hash, which dominates seed time and is rarely what stress-testing the design needs.

9. ICS "open with"

There is no web API to raise the OS app picker. The link currently carries download, which forces a save. Removing it and serving the file inline is the closest thing: the OS hands the .ics to whatever is registered, which on desktop is usually a chooser.

10. Player stat grid — dropped cells

Your three rows list 11 cells and none of them is Match Losses or Game Losses, which exist today. I will not silently delete a metric.

11. Logout return contract

Logout currently goes to /. Your rule sends it to sign-in and back to "the previous page where the user clicked logout" — but that page is often one that requires the session you just ended.

12. "Starting Hour" timezone

Events carry a venue IANA timezone; the app already renders both a venue time and a viewer time, and the two differ for anyone browsing from another country.

13. Anonymous register flow

Today the intent round-trips back to the calendar list and opens a confirm dialog there. Your text says the sign-in should redirect to the event page to confirm.

14. Removing the public Organizations pages

You asked to delete the second Organizations button and the /organizations page. That page's detail route is also the only management screen the "My organizations" page links to, so deleting the list alone would strand it.

15. Back button — edge pages

Fifteen routed pages have no back button and three have top-only. The awkward ones are sign-in/register (where a back button competes with the sign-in flow), the Live runner (long scroll, has its own footer), and modal dialogs (not pages).
