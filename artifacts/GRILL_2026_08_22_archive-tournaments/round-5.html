Why locking needs its own round

Your precision: "After a full year—365 days—the data should be locked so that only the admin can update it directly in the database… Data locked locally never needs to be refetched again in the same browser… you can remove from the request all data that has been locked, which optimizes the fetching."

The intent is clear and the optimisation is real. But there is no lock, freeze or immutability concept anywhere in this codebase — I checked the whole domain and API layer; the only hits are unrelated Live-tournament pairing locks. So every part of it is new, and one part is a trap: "locked data is never refetched" plus "an admin can still change it" means an admin edit can never reach any browser that already cached that year. Q4 is the escape hatch, and it is not optional.

1. What is the unit of locking?

"Locked" has to attach to something. The cache entry is a year, so a lock that does not align with a year makes the entry partly-stale — which is the one state the optimisation cannot express.

2. What does "locked" mean on the server?

You said only an admin can update locked data "directly in the database". That could mean the API refuses those writes, or that it is a convention nothing enforces. Only the first is testable.

3. Does locking apply to the browser-local archive?

Round 1 Q10 kept the dual-source rule: browser-local Seasons and Tournaments exist alongside server ones. Locking is a server-authority idea, so its meaning for local rows has to be stated.

4. How does an admin change reach an already-cached locked year?

The trap. "Locked years are never refetched in this browser" plus "an admin can still change them" means a corrected 2024 result is invisible forever to everyone who visited before the fix. This needs a cheap escape hatch, or locking becomes a permanent-divergence bug.

5. How does the async backfill behave?

You specified it must not impair navigation and must be independent of the current-year fetch. Order, visibility and failure behaviour still need pinning.

6. Final route and segment names

You asked to rename the API and URL routes to leagueSeason. This codebase spells every route segment in kebab-case — /api/leagues-archive, /api/live-tournaments, /api/event-proposals — so the literal camelCase form would be the only exception in the app.
