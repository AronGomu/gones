Gones · Architecture

Player Statistics Read Model

Both readers used to recompute everything from whole league documents on every view. Tournaments land a few times a week; pages are viewed constantly. Move the cost to the write: materialize once, read an index. Scope is the completed Archive Tournament — a word the domain had to grow first.

What was wrong

O(all data) Global Rankings

GET /api/leagues-archive/global-player-statistics loaded every completed LeagueArchiveAggregate document into memory, walked every round of every tournament, then filtered, sorted and paged in process. Per request. No cache, no index.

O(all data) Player page

/players/:name called repo.listLeagues(), downloaded the whole corpus to the browser, and ran calculatePlayerStatistics there. Megabytes to a phone, to render twenty numbers and a list.

disagreement Two scopes

Rankings counted completed leagues. The player page counted all leagues. The same player could hold two different win rates depending on which page you opened.

The word the domain was missing

The chosen scope is "only completed Tournaments". That granularity did not exist:

// before
public sealed record TournamentDocument(
    string Id, string LeagueId, string Name, string TournamentDate,
    IReadOnlyList<RoundDocument> Rounds,
    IReadOnlyList<PlayerArchetypeDocument> PlayerArchetypes);   // no status, no completedAt

public sealed record LeagueDocument(
    string Id, string Name, string Status, …);                   // 'active' | 'completed' — here only

Deriving it was not safe. Match scores are plain integers, so an unscored match and a genuine 0–0 are identical bytes. A rule like "completed when every match has a score" would silently disqualify a real double no-show — and a tournament would vanish from every statistic with no error anywhere.

So the flag is explicit, set by a human, and reversible.

Note this default is the opposite of normalizeLeagueStatus, deliberately: an archive is history, and history is finished.

One writer, three readers

Why synchronous, in-transaction

chosen In the write transaction

No staleness window. No scheduler. A failed archive write rolls the statistics back with it, so the table can never disagree with the archive it summarises. One rare operation gets slower.

Rejected: dirty flag, rebuild on read

Keeps the write instant, then hands an unbounded cost to a random unlucky visitor's page load.

Rejected: background job

Smoothest latency, but adds a scheduler dependency and a visible window where an organizer's just-committed results are missing from the rankings.

The repair path

A rebuild inside the write transaction covers every data change. It covers no code change — fix a bug in the win-rate maths and every untouched player keeps the old number, with nothing to trigger a repair. The first deploy has the same problem: the table starts empty and no archive write is coming.

startup → read player_statistics_meta.FormulaVersion
≠ PlayerStatisticsFormula.Version, or no row → rebuild, update meta, then serve traffic
= → skip, serve immediately
Gones:PlayerStatistics:RebuildOnStartup = false → never rebuild (escape hatch)

Bump PlayerStatisticsFormula.Version in the same commit as any change to the statistics maths. That constant is the only thing standing between a formula fix and a table full of numbers computed by the old one.

Likewise, any path that writes archives outside a domain transaction — the bulk-SQL stress seeder is the only one — must trigger a rebuild explicitly and assert a non-zero row count.

What the browser still does

The match history ships flat and whole: one row per match with league and tournament flattened to ids and names, plus both deck archetypes resolved server-side. The browser keeps every feature it already had — filter tokens, search highlighting, newest/oldest, page size, pagination — because none of that needed the documents, only the rows.

PlayerMatchRow {
  kind: 'match' | 'bye';
  leagueId; leagueName; tournamentId; tournamentName; tournamentDate;
  roundIndex; opponentName; ownScore; opponentScore;
  ownArchetype; opponentArchetype;   // "" when unknown, never null
}

What a row holds

Two groups, filled by the same rebuild in the same transaction. The counting pass came with ADR 0040 at formula version 1; the rating replay came with ADR 0043 and took the table to formula version 2.

rating_deviation, rating_volatilityv2 ratingSeeded at 350 / 0.06; the deviation is clamped at 350

The six unindexed rating columns are deliberate: they are read back with a row that has already been found, so an index on them would only cost rebuild time.

Browser-local leagues keep counting. ADR 0028 archives live only in this browser and never reach the server, so the read model cannot see them. The Online only toggle stays: ON shows the server table verbatim; OFF computes the local half in the browser and merges it into the totals and the history, marking each local match. Derived ratios are recomputed from the merged counts — never averaged from two summaries.

Consequences worth stating out loud

  • Numbers change on first deploy. Scope moves from league-level to tournament-level completion. That is the decision, not a regression.
  • Rankings and the player page can no longer disagree: they read the same row.
  • An organizer entering rounds over several evenings sees nothing counted until they mark the tournament complete — which is the point.
  • The measured 100× startup-rebuild duration belongs in ADR 0040. If it blows the container start budget, the rebuild moves into the migrator service, which already runs one-shot before the API; the code path is identical. Same dataset, 1183 rows from 201 Leagues: 177 ms at version 1, 196 ms at version 2 with the rating replay (ADR 0043).
