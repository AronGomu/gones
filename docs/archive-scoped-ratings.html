Gones · Architecture

Scoped Player Ratings

A Glicko-2 rating is the end of a replay, not a sum of matches. You cannot filter a global rating down to one League — you have to replay that League on its own. So the read model stops being one row per player and becomes one row per scope per player, keyed (scope_kind, scope_id, player_name), and the rankings filter selects a key instead of narrowing a result.

Why a filter cannot be a filter

The obvious design is a WHERE league_id = … on the rankings query. It works for counting columns and is wrong for every other one.

impossible Rating

Glicko-2 is path-dependent. The rating after a Match depends on the deviation the player carried into it, which depends on every earlier rating period. Drop the Tournaments outside the League and every remaining update was computed against the wrong prior. There is no arithmetic that recovers the League-only rating from the global one.

wrong Winrate

match_winrate is a ratio, and ratios do not filter. Narrowing to a League means recounting wins and played matches inside it and dividing again — averaging the global ratio against anything is a different number that happens to look plausible.

misleading Matches · Tournaments

These two could be filtered if the read model kept per-match rows — it does not, by design (ADR 0040 moved the cost to the write). Serving a scoped rating beside a global match count would put two different scopes in one row, which is exactly the disagreement ADR 0040 was written to end.

So every displayed number is recomputed within the scope. Rating, deviation, volatility, previous rating and last delta; matches played, wins, losses, draws and match winrate; games and game winrate; tournaments played; last played date; nemesis, rival and most-played archetype. A league row is what that player's career would look like if that League were the whole world.

The key

player_statistics keeps every column it has (see backend/src/Gones.Infrastructure/Persistence/PlayerStatisticsReadModel.cs) and gains two in front of them. The primary key stops being player_name alone.

scope_id is '', never null. A nullable component in a primary key is a constraint Postgres will not enforce the way this table needs. The empty string is a real value, is unique per scope_kind = 'global', and makes the global row addressable by the same three-column lookup as every other row — no special case in the query, no IS NULL branch.

One rebuild, one row per scope per player

The writer does not change shape. PlayerStatisticsRebuildService still rewrites the whole table wholesale, still inside the caller's transaction, still without calling SaveChangesAsync itself — so a failed archive write rolls the statistics back with it and the table can never disagree with the archive it summarises. What changes is how many rows come out of one pass.

Row count grows with participation, not with the square of anything: a player appears once globally, once per League they played in, and once per Season of those Leagues. A player who only ever entered standalone Tournaments has exactly one row.

Bump PlayerStatisticsFormula.Version in the same commit. The constant is at backend/src/Gones.Domain/Leagues/PlayerStatisticsFormula.cs and reads 2 today — version 1 was the ADR 0040 counting pass, version 2 added the ADR 0043 Glicko-2 replay. Scoping is a change to what the maths covers, so it takes the next number, and that is the only thing that makes PlayerStatisticsStartupRebuild repair rows already in the table. Forgetting the bump leaves a database full of unscoped rows with nothing anywhere to trigger a repair.

The rebuild also still takes its transaction-scoped advisory lock before the DELETE FROM player_statistics. Two transactions editing different parts of the archive both rewrite the whole table; without the lock the loser's delete is evaluated against a pre-commit snapshot and it re-inserts the same keys on top of the winner's rows — a duplicate key on pk_player_statistics, which turns a legal archive write into a 500. A wider primary key does not change that; it widens the key that collides.

Standalone Tournaments feed the global scope only

A Tournament with seasonId: null belongs to no Season, and because a Tournament has no leagueId column at all, it belongs to no League either. There is no league row and no season row for it to feed. It counts globally and nowhere else — not in a catch-all scope, not under a placeholder id.

tournament.seasonId != null → global row · league row (via season.leagueId) · season row
tournament.seasonId == null → global row only

The practical reading: switching the rankings from All Leagues to any single League can only ever lose matches, never gain them, and a player whose whole record is standalone events disappears from every scoped view. That is correct, and the scope badge is what stops it being surprising.

Single-select, at both levels

The filter offers All or exactly one League, and All or exactly one Season. There is no multi-select, and the reason is structural rather than a UI preference: a scope is a stored row key. Two Leagues selected at once name a scope that was never rebuilt, so the server would have to merge two rating rows at read time — the exact operation the first section of this document says does not exist. A multi-select control would promise a number the read model cannot produce.

The Season selection is the narrower scope, so when both are set the Season wins; the League select then acts as what it is, a way to shorten the Season list. Two selects collapse to exactly one (scopeKind, scopeId) pair, always — which is the invariant that lets the whole feature be a primary-key lookup.

The scope badge

The rankings page states its scope in words, next to the table, at all times. Without it, a narrowed board is indistinguishable from a broken one: the ratings move, the player list shrinks, and nothing on screen says why.

It is built from the app's existing .status / .status-dot chip (src/styles.css:42-45) and uses the same two tokens the rest of the app uses for that distinction — --create-green for the unrestricted default, --hot-blood once a scope narrows the board. The badge names both levels even when one is All, so the global state reads as a deliberate choice rather than an absence.

An unknown scope is an empty page, not an error. scopeKind=league or season with a scopeId that has no rows answers 200 with an empty page. A League that exists but whose Tournaments are all still active is a legitimate, common state — a 404 there would tell the user the League is missing when it is merely young. A scopeKind outside global | league | season is a 400 validation_failed, because that one is a caller bug.

The URL says dir; the wire says direction. Archive tabs and /global-stats agree on ?dir= in the address bar, while the query parameter sent to the API stays direction — which is what the endpoint binds today (backend/src/Gones.Api/Leagues/PublicLeagueEndpoints.cs:104, string? direction). The rankings page currently writes direction= into its own URL (src/app/features/players/global-stats-query.ts:196, asserted at cypress/e2e/global-stats.cy.js:76-78); renaming it is a user-visible URL change to a shipped page, accepted because Gones is unreleased and has no users.

Two page-size defaults, both deliberate. The rankings keep pageSize=100, which is what PublicLeagueEndpoints.GlobalStatsDefaultPageSize is today. The archive table tabs default to size=25. Different surfaces, different reading habits.

The sort vocabulary above is the short one. The shipped endpoint allowlists the column names verbatim — playedMatchCount, matchWins, matchLosses, matchDraws, matchWinrate, playedGameCount, gameWins, gameLosses, gameWinrate, rating, tournamentsPlayed, plus decayedRating when Gones:PlayerStatistics:ExposeDecayedRating is on (PublicLeagueEndpoints.cs:36-41). The scoped route takes the shorter names, so the mapping between the two lives at the endpoint and the game-level columns keep their existing keys unless something explicitly retires them.

Response, caching and the catalog twin

The body is the existing paged global-statistics response, field for field — { items, page, pageSize, totalCount, sort, direction } over GlobalPlayerStatisticsRow. Only the scope selection is new. Both rankings routes serve Cache-Control: public, max-age=60 with an ETag and a 304; the catalog twin is capped by the existing Gones:GlobalStats:MaximumCatalogSize, default 5000.

the request date is in there because provisional and inactive are derived at read time

Provisional (fewer than 5 Tournaments played) and inactive (no completed Tournament in 12 months) stay derived at read time from tournaments_played and last_played_date plus the request clock, per ADR 0043 — and they are now derived per scope, which is the honest answer: a player with forty global Tournaments and two in this League is provisional in this League. The default three-bucket order is unchanged: active ranked by rating desc, then inactive ranked, then provisional by tournaments played then matches played, every tie broken on the ordinal player name.

Consequences worth stating out loud

  • The same player holds several ratings at once, and they are all correct. A global 1712 and a League 1588 are answers to two different questions. The badge is what keeps the page from looking like it contradicts itself.
  • A scoped rating is a smaller replay, so it is a less confident one. Fewer rating periods mean a higher deviation, and a player ranked in the global board can be provisional in a League board. Nothing hides that; the provisional badge is per scope like everything else.
  • Rebuild cost scales with the number of scopes, not with archive size alone. The measured baseline is 1183 rows from 201 Leagues in 196 ms at formula version 2. Every League and every Season adds a replay over its own subset — the sum of the subsets is bounded by the archive walked once per tier, but the constant is real and belongs in the ADR that lands this.
  • The existing single-column indexes no longer serve a scoped ordering on their own. PlayerStatisticsReadModelConfigurations.cs indexes each sortable column singly — rating, tournaments_played, the nine counting columns — which was exactly right for a table that was always read whole. A scoped query filters on the composite key prefix first, so the ordering index must be reached after that filter. Worth measuring against a seeded stress environment before deciding whether any of them needs a (scope_kind, scope_id, …) prefix.
  • Browser-local records still never reach the read model. ADR 0028 archives live only in this browser and are never sent to a server, so no scope of any kind can see them. The Online only toggle keeps its ADR 0043 behaviour: the rating shown is the server's, and local Matches never move it.

Re-keys the read model of ADR 0040 and the Glicko-2 replay of 0043; bounded by 0028 (browser-local archives never contribute) and 0039 (public catalog caching).
