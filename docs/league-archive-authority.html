League Archive Authority

The League Archive reads from two stores and writes to one. Which one is decided by the league's own id, not by who is asking. That is the difference from Live Tournaments, and it exists for exactly one reason: export must not lose what the browser holds.

Origin lives in the id

There is no origin column, no lookup table, no second source of truth about where a league lives. A league's id says it:

local-9f2c1a7e-…       browser-local league
local-placeholder-league   browser-local "Unassigned Tournaments" bucket
placeholder-league         the server's fixed bucket
7f3a…                      server league

One predicate is the whole routing layer:

// src/app/data/league-archive-origin.ts
export function isLocalLeagueId(id) { return id?.startsWith('local-') ?? false; }
Why an id prefix. Any other marker — a field on the document, a set held beside the store, a probe of both backends — can drift out of sync with reality. A prefix cannot: it travels with every reference to the league, including router URLs, export bundles and error messages, and it is impossible to hold a league id without also holding its origin.

Two stores, one facade

server AspNetApiBackend

Bound to LEAGUE_ARCHIVE_BACKEND. Unchanged by ADR 0028. Every mutation is an intent command guarded by an If-Match ETag. Audited, shareable, survives the browser.

local LocalLeagueArchiveBackend

IndexedDB gones-leagues / leagues, key path id. Strictly offline — no HTTP dependency exists to inject. Every write passes one mutate() helper that guards documentVersion and stamps updatedAt.

LeagueArchiveRepository is where the two meet. It is the only place that knows there are two:

listLeagues() → Promise.allSettled([server.list(), local.list()]) → concat
server rejected + local ok → local rows only, serverUnavailable = true
both rejected → rethrow
getLeague(id) / every write → port(id) = isLocalLeagueId(id) ? local : server
createLeague(name) → createLeagueTarget(role) — the one call with no id to route on
saveTournamentEdits() → one routed batch → one DB / IndexedDB readwrite transaction
same League → source +1, destination null
same-authority move → lock/read both by id → validate both versions → put both → commit
stale / invalid / put fail → abort → neither League changes

Parity is a compiler check, not a promise

export class LocalLeagueArchiveBackend implements LeagueArchiveBackendPort { … }

All 21 methods, no Partial. If someone adds a capability to the port and implements it only on the server, npm run typecheck fails. A feature cannot quietly become "signed-in only".

Permission is per league, not per session

export function canManageLeague(leagueId, role) {
  return isLocalLeagueId(leagueId) || canManageLeagues(role);
}

A plain User therefore sees one grid holding two kinds of row: server leagues they can only read, and their own browser leagues they fully own. The Local only badge is not decoration — it is the user-facing form of this rule.

How this differs from Live Tournaments

Do not harmonise these. The shapes differ because the requirements differ: League export had to include browser-held data, Live export did not. Making one look like the other needs a new ADR, not a refactor.

Explicit staged Tournament edits

Archive Tournament detail is read-only by default. An authorized Power User enters one explicit edit session; name, date, same-authority League target, rounds, entries/imports, and archetypes mutate one browser-memory draft. No adapter call occurs before confirmed Save Changes.

Edit → clone authoritative League into one draft
Cancel dirty draft → confirmation → discard without repository call
Save empty diff → exit edit mode without repository call
Save dirty diff → one summary dialog → one saveTournamentEdits() batch
validation / network / 412 → preserve draft; never auto-merge or retry
Reload Latest cancel → keep draft; confirm → reload authoritative versions, discard, exit

The League selector contains active destinations from the source League's authority only. Whole Tournament and League deletion remain separate header actions with separate confirmations.

What "the database always prevails" means here

It is a command discipline, not a background reconciler:

  • Every mutation is an explicit intent command guarded by documentVersion.
  • Every command returns the store's own persisted document, and the caller replaces its in-memory state with that value. No whole-document save, no optimistic edit kept afterwards.
  • A rejected command (412) is surfaced as "reload and reapply", never merged.

Both adapters raise the same conflict shape, so the UX is identical on either side:

LeagueConcurrencyError { status: 412, message: 'staleLeagueDocument' }
  → leagueCommandError(error) === 'stale'

Accepted costs

  • The stores never converge. A league created signed out stays in that browser unless it is exported and re-imported while signed in. That round trip is the only bridge, and it is deliberate, explicit and user-driven.
  • Clearing site data destroys local leagues. There is no server copy. The list page says so; export is the backup.
  • Local edit batches and moves are atomic. Source and target reads, version checks, transforms, and puts share one IndexedDB readwrite transaction. Request, validation, stale-version, or action failure aborts without changing either row.
