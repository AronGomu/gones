Event Proposal Flow

One creation page for every role. Organizers and admins publish. Everyone else with a verified account proposes, and a reviewer decides from a link in their inbox — no login required.

The proposal path, end to end

  1. Fill the formSame component, same FormGroup, same validator as direct publishing. Nothing about the payload differs.
  2. Submit → approver dialogGET /api/event-proposals/approvers returns every Organizer and Admin as { id, username, globalRole }. Never an email address. Admins listed first.
  3. Check one or more, sendPOST /api/event-proposals with the event payload and recipientUserIds. Confirm is disabled until at least one box is checked.
  4. Server stores the payloadAn event_proposals row holds the payload as jsonb with a 7-day expiry. It is not a draft event — there is no path from a pending proposal into the public calendar.
  5. One token per recipient32 random bytes, base64url. The database stores only sha256(token). The plaintext exists in exactly one place: the link in that recipient's email.
  6. Emails go out through the outboxTemplate tournament-proposal, recipient's locale, dedupe key tournament-proposal:{proposalId}:{userId}. Body carries every submitted field. The template and dedupe keys keep their pre-rename names on purpose (ADR 0035): renaming a dedupe key re-sends mail already deduplicated under the old one.
  7. Reviewer opens the link/event-requests/{token} — anonymous route, no guard, renders signed out. /tournament-requests/{token} permanently redirects to it.
  8. Validate or RefuseApprove publishes with the submitter as acting user. Refuse opens a reason textarea and mails it back.

What the reviewer sees

review

Title, submitter, venue, dates, formats, capacity, and the description rendered as plain text. Two buttons: Valider, Refuser.

reason

A textarea (1–2000 chars) and Envoyer Email Raisons Annulation, disabled while empty.

expired / handled

404 → link expired. 409 → another reviewer already decided. Neither leaks the payload.

Plain text, deliberately. Server-side HTML sanitization lives behind an organizer-only preview endpoint. An anonymous page must not call it, so the review page renders the description in a <pre>. The reviewer loses formatting, not information.

The race that cannot happen

Reviewer A (token a)          Reviewer B (token b)
────────────────────          ────────────────────
POST .../approve
  load proposal (Pending)
                              POST .../approve
                                load proposal (Pending)
  publish + Approve()
  SaveChanges  ✔ 200
                                SaveChanges → concurrency conflict
                                → 409 Conflict, nothing published

Result: exactly one public event.

The proposal row's optimistic-concurrency version is the arbiter. A DbUpdateConcurrencyException maps to ResourceConflictException, and the page switches to its already handled state.
