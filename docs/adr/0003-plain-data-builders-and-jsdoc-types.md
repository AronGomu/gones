# Plain Data Builders and JSDoc Types

Status: superseded by [ADR 0009](./0009-use-modern-angular-with-signals-and-typescript-domain.md) for the Angular/TypeScript migration.

Gones source data will be represented as plain JavaScript objects rather than domain classes, with builder functions used where constructor-like defaults or safe structural normalization are useful. Builders fill defaults and normalize source data, while validity decisions belong in domain validation functions. ID and time generation should be passed into builders or isolated at builder boundaries so result calculations remain deterministic. Domain source data uses camelCase field names; import/export adapters translate external formats into those shapes. New URL parameters also use camelCase, while legacy snake_case parameters may be supported during migration. Round Entry fields are shaped by their `kind`: matches use `player1Name`, `player2Name`, `player1Score`, and `player2Score`; byes use `playerName`; invalid entries may keep `rawText` plus optional edited fields matching the possible target shape. Rounds and Round Entries have IDs so editing and deletion can target stable source data rather than array indexes; displayed round numbers are derived from Round order. Exported League data may include IDs for internal coherence, but restore remaps them when creating a new League in the current app. Domain shapes should be documented with JSDoc typedefs so the code has TypeScript-like interface clarity without adding a build step. Typedefs live beside the builder or calculation module that owns the shape, such as source-data typedefs near builders and result-view typedefs near result calculators. Existing class-based models may be replaced incrementally, but the end state is one source model under the domain layer, not parallel class and plain-object models. This keeps export, restore, versioning, and recalculation centered on serializable data while still giving contributors explicit data contracts.
