Gones · Architecture

Calendar Data Flow

One request a day fetches every present-and-future event. Everything the user types after that filters a local array. The month grid never disappears.

Before and after

Was

  • Six filter inputs + an Appliquer button
  • Each apply = a router navigation + a paged request
  • Server-side WHERE per field, exact match
  • Month change = another request
  • Zero results = no calendar at all

Is

  • One search input, full page width
  • One request per 24 h, plus a manual Synchroniser
  • Client-side fuzzy match across every field but the description
  • Month change = zero network
  • Zero results = the grid renders, empty, with a notice below it

The read pipeline

PublicCalendarComponent — searchDraft(), month, view signals

PostgreSQL events ⋈ organizations

Search-term grammar

Separators are ,, ; and whitespace. A backslash escapes the next character, so a separator can be part of a term. Terms are ANDed.

InputTermsMatches
lyon['lyon']anything in Lyon
lyon, legacy['lyon','legacy']Legacy events in Lyon
saint\,étienne['saint,étienne']the literal string, comma included
grand\ prix['grand prix']the phrase, not two words
RHONE['rhone']matches Rhône — accents and case folded
2026-09-12['2026-09-12']that venue date

The bulk endpoint

GET /api/events/all?from=2026-08-08               # anonymous

200 OK
ETag: "9f2c…"                                     # sha256(count : maxUpdatedAt : lastId)
Cache-Control: public, max-age=3600
{
  "items":       [ …PublicEventSummaryResponse… ],
  "generatedAt": "2026-08-08T09:14:02Z",
  "count":       137,
  "truncated":   false
}

304 Not Modified                                  # when If-None-Match matches
Ceiling, not a cliff. Gones:Calendar:MaximumCatalogSize defaults to 5000. Past it the response is capped, truncated flips to true, the server logs a warning and the page renders a visible notice. Silent truncation would read as "you have seen everything" when you have not.

Page layout — what the pipeline feeds

The catalogue above is one fetch. The page then splits it across two tabs that consume it very differently. Document order on /calendar:

The grid's geometry is month-only; its contents are not. buildMonthDays(month) still takes a month and nothing else, so the shape of the grid never depends on the filtered set. The cells themselves do carry events: each renders up to MAX_DAY_CELL_EVENTS (3) links from dayEventIndex, which is built over the filtered items(), plus a “+N more” line past that. Typing therefore re-renders the cell contents while the grid keeps its size and position.
Past days are dimmed with a tint, never with opacity. A blanket opacity drags the day number under the contrast floor. .public-month-day--past darkens the cell background with color-mix and sets the day number to var(--steel) at weight 700 — measured 5.49–5.62:1, AA at every cell tone. A vitest assertion in public-calendar.component.test.ts fails if an opacity rule reappears on that selector.
Month navigation preserves the scroll position. Month change is a query-param navigation on the same route, which the router's scrollPositionRestoration treats as a fresh page. moveMonth() captures window.scrollY, pins the grid height so the document cannot shrink underneath it, navigates with scroll: 'manual' for that one navigation, and restores the offset on the next frame.

What the filter still drives

searchDraft() → filterEvents(allItems(), q) → items()
items() → empty-state panel both tabs
items() → sortEventsForList() → paginateEvents(…, page) → groups() list tab
items() → eventsByDate() → dayEventIndex() → day-cell links calendar tab
the grid's shape reads none of the above — only query().month

The search text is debounced 300 ms into the q query parameter. Changing q, month or view resets page to 1; page 1 is never written to the URL, so a shared link stays clean.

Pagination

SymbolWhereRule
PAGE_SIZEpublic-calendar.ts20
sortEventsForListsamevenue date, then start time, then title, then id — a stable flat order is what makes paging deterministic
calendarPageCountsamemax(1, ceil(total / 20)) — an empty list is still one page
clampCalendarPagesameout-of-range, fractional and NaN pages resolve to a real page
paginateEventssameslices after clamping, so a hand-edited URL never renders an empty list

Grouping happens after paging: the 20 events of the current page are then split into venue-date sections. Paging by group would give pages of wildly different sizes.

Matched text

Titles rendered in the day cells and in the list are split by highlightSearchText() (src/app/shared/search-highlight.ts) into plain and matched parts, and the matched parts carry .match-highlight. The search itself is still the fuzzy filter above; highlighting is a presentation pass over the same terms.

Boundary rules this respects

  • Read-only. Nothing here writes; publication still goes through the organizer endpoints or the proposal flow.
  • Filtering, sorting and paging are pure functions over the cached snapshot. No request is issued by typing, by turning a page or by changing month — only Synchronise and a cache miss reach the network.
  • localStorage holds a cache of anonymous GET responses and nothing else — the same justification the pre-existing entries in the server-authority-boundary.test.ts allowlist carry. It is never a mutation source.
  • The paged GET /api/events stays, contract-tested. It is the documented public read API; this application simply no longer calls it.
